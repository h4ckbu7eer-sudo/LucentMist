## 安装与编译

### Q1: dotnet build 报错 "SDK 版本不对"？

**完整错误示例**：
```
error NETSDK1045: 当前 .NET SDK 不支持将 .NET 8.0 设置为目标。
```

**原因**：系统安装的 .NET SDK 版本低于 8.0。

**解决步骤**：
```bash
# 1. 查看当前版本
dotnet --version
dotnet --list-sdks

# 2. 如果版本 < 8.0，下载安装 .NET 8.0 SDK
# 下载地址: https://dotnet.microsoft.com/download/dotnet/8.0
# 选择对应操作系统: Windows x64 / Linux / macOS

# 3. 安装后重新打开终端，确认版本
dotnet --version  # 应显示 8.0.x

# 4. 清理并重建
dotnet clean
dotnet restore
dotnet build
```

### Q2: NuGet 还原失败，下载不到包？

**原因**：网络问题或 NuGet 源不可达。

**解决**：
```bash
# 方法1: 检查 NuGet 源
dotnet nuget list source

# 方法2: 使用代理（如果在国内）
# 配置 NuGet 镜像源（如阿里云）
dotnet nuget add source https://api.nuget.org/v3/index.json -n nuget.org

# 方法3: 手动还原单个项目
dotnet restore src/LucentMist.Core/LucentMist.Core.csproj --verbosity detailed

# 方法4: 清除缓存后重试
dotnet nuget locals all --clear
dotnet restore
```

---

### Q3: 项目编译通过但 tests 失败？

**完整排查**：
```bash
# 1. 查看详细失败信息
dotnet test --verbosity detailed

# 2. 单独运行失败的测试
dotnet test --filter "FullyQualifiedName=LucentMist.Core.Tests.MemoryStoreTests.StoreAndRetrieve_ShouldWork"

# 3. 如果是 MemoryStore 测试失败：检查内存是否充足
# 如果是 SessionManager 测试失败：通常是瞬态问题，重试
dotnet test --retry 3
```

## 扫描功能

### Q5: 扫描结果为 0 台设备？

**现象**：
```text
┌────────────┬──────┐
│ 扫描 IP 数 │ 254  │
│ 在线设备数 │ 0    │
└────────────┴──────┘
```

**排查流程**（按顺序执行）：

```bash
# 1. 确认网络正常
ping 8.8.8.8                  # 外网通吗？
ping 192.168.1.1               # 路由器通吗？

# 2. 确认子网正确
ipconfig                       # Windows
# 或 ifconfig                  # Linux/macOS
# 找到 IPv4 地址和子网掩码
# 例: 192.168.56.46 / 255.255.255.0 → 子网 192.168.56.0/24

# 3. 测试本机（100% 能通）
dotnet run --project src/LucentMist.CLI -- scan 127.0.0.1
# 预期: 在线设备数 1

# 4. 本机能通但局域网不通 → 可能原因:
#    - 子网填错了（不是你实际在的网段）
#    - Windows 防火墙阻止了 ICMP
#    - 路由器配置了隔离（AP Isolation）
#    - 使用的是虚拟机网络（VMware 虚拟网卡）

# 5. 如果是 WiFi，尝试:
#    - 关闭路由器 AP 隔离功能
#    - 连接有线网络测试
#    - 确认不是访客网络（Guest Network）
```

---

### Q6: 端口扫描没有开放端口？

**排查**：
```bash
# 1. 确认目标在线（先 ping）
# 2. 扫描本机测试
dotnet run --project src/LucentMist.CLI -- scan 127.0.0.1

# 3. 检查常见端口: 22(SSH), 80/443(Web), 3389(RDP), 445(SMB)
# 4. Windows 设备默认防火墙会阻止大部分端口
# 5. Linux 设备可能只开了 SSH
```

---

### Q7: 扫描速度很慢（/24 网段超过 30 秒）？

**原因分析**：
- /24 = 254 个 IP × 每个 2 秒超时 = 最坏 508 秒
- 实际有并发优化，但 WiFi 延迟高会影响速度

**优化方案**：
```json
// 编辑 config/appsettings.json
{
  "Scan": {
    "DefaultTimeoutMs": 2000,   // 降到 2 秒（局域网够用）
    "MaxConcurrency": 200       // 增大并发（有线可到 500）
  }
}
```

```bash
# 或者缩小范围
dotnet run --project src/LucentMist.CLI -- scan 192.168.56.0/28  # 14 个 IP
```

### Q8: 可以扫描公网 IP 吗？

**A**：技术上可以，但**强烈不建议**：
1. 扫描他人 IP 可能违法（计算机入侵罪）
2. 公网扫描会被目标防火墙检测并封禁你的 IP
3. LucentMist 设计用于**局域网**场景

**如果你确实需要测试（比如扫自己的云服务器）**：
```bash
# 只扫描指定端口，不要扫全范围
dotnet run --project src/LucentMist.CLI -- scan <你的服务器IP>
```

## Agent AI 功能

### Q9: Agent 命令提示 "请配置 LLM Provider"？

**A**：Agent 需要 Ollama 或 Claude API。

```bash
# 步骤1: 安装并启动 Ollama
ollama serve                              # 监听 localhost:11434

# 步骤2: 下载推荐模型
ollama pull llama3.1:8b                  # 约 5GB，需几分钟

# 步骤3: 验证
ollama list                               # 确认模型在列表中

# 步骤4: 测试 Agent
dotnet run --project src/LucentMist.CLI -- agent "扫描127.0.0.1的端口"
```

---

### Q10: Agent 显示 "无法解析 LLM 输出" 是什么意思？

**现象**：
```text
  [1] 无法解析 LLM 输出
```

**原因**：LLM 返回的文本不是合法的 JSON 格式。ReAct 引擎需要严格的 JSON 来提取 `thought/action/action_input`。

**可能原因与解决**：

| 原因 | 表现 | 解决 |
|------|------|------|
| 模型太小 | moondream 1B 参数无法输出结构化 JSON | 换成 llama3.1:8b |
| 网络问题 | Ollama 响应被截断 | 检查网络，重试 |
| Prompt 格式 | system_prompt.txt 不够严格 | 已优化，重新拉代码 |
| 模型加载中 | 首次请求超时 | 重试（第二次会快很多） |

**验证模型是否正常**：
```bash
ollama run llama3.1:8b '输出JSON: {"name":"test"}'
# 看它能否正确输出 JSON
```

### Q11: Agent 编造了不存在的端口信息？

**现象**：Agent 说某个 IP 开了 80/443/22 端口，但实际没开。

**原因**：这是 LLM 的**幻觉（Hallucination）**——当工具没有实际执行时，LLM 会根据自己的训练数据猜测。

**如何判断 Agent 是否真的扫了**：

```text
真扫描（可信）：
  [1] 需要扫描端口                         ← 思考
      -> port_scan                          ← 实际调用了工具
      目标     192.168.56.231
      开放     1 个端口                     ← 工具返回的真实数据

假扫描（不可信）：
  [1] 用户问扫描端口，我猜有80、443、22     ← 没有工具调用！
      -> final_answer
      开放了80、443、22                     ← 编造的
```

**解决方法**：
1. 确认推理过程中有 `-> port_scan` 这样的工具调用行
2. 如果只有 `-> final_answer` 没有工具调用 → 数据不可信
3. 重新运行，确保 Ollama 正常工作

### Q12: Agent 首次运行一直转圈？

**现象**：启动后 Spinner 转了超过 2 分钟没有输出。

**原因**：llama3.1:8b 模型 4.9GB，首次加载到 GPU 显存需要 30-120 秒。

**解决**：
```bash
# 先手动预热模型
ollama run llama3.1:8b "hello"
# 等待回复后再用 LucentMist Agent
# 第二次就会很快（2-10 秒）
```

**如果超过 5 分钟还没响应**：
```bash
# 1. 检查 Ollama 进程
# 2. 检查显存是否足够（llama3.1:8b 需要 ~5GB）
nvidia-smi  # 查看 GPU 显存使用
# 3. 如果显存不够，Ollama 会用 CPU 推理（慢 10-50 倍）
```

### Q13: 如何切换 Ollama / Claude？

```bash
# 方式1: 修改配置文件
# config/appsettings.json
{
  "LucentMist": {
    "LLM": {
      "Provider": "ollama",           // 改这里
      "Model": "llama3.1:8b"          // 改这里
    }
  }
}

# 方式2: 环境变量（临时覆盖）
export LucentMist__LLM__Provider=claude
export LucentMist__LLM__ClaudeApiKey=sk-ant-api03-xxx
```

## 模型相关

### Q14: 推荐用哪个模型？

**实测数据**（RTX 4050 Laptop, 6GB VRAM）：

| 模型 | 大小 | 加载时间 | 推理速度 | JSON格式 | ReAct可用 | 推荐 |
|------|------|----------|----------|:--------:|:---------:|:----:|
| moondream:latest | 1.7 GB | 5s | 快 | 否 | 否 | 否 |
| **llama3.1:8b** | **4.9 GB** | **60s** | **中** | **是** | **是** | **是** |
| llava-llama3:8b | 5.5 GB | 90s | 慢 | 是 | 是 | 备选 |
| qwen2.5:7b | ~4.5 GB | 50s | 中 | 是 | 是 | 备选 |

**结论**：llama3.1:8b 是目前实测最稳定的选择。

## 性能调优

### Q17: 端口扫描为什么这么慢？

TCP Connect 扫描每个端口需要进行 TCP 三次握手：
```
客户端 → SYN → 目标
客户端 ← SYN-ACK ← 目标 (端口开放)
客户端 ← RST ← 目标 (端口关闭，或无响应超时)
```

1000 个端口 × 2 秒超时（默认）= 最多 2000 秒。

**优化建议**：
```json
// config/appsettings.json
{
  "Scan": {
    "DefaultTimeoutMs": 1000,   // 局域网 1 秒足够
    "MaxConcurrency": 200,      // 提高到 200 并发
    "DefaultPorts": "1-100"     // 只扫描常用端口段
  }
}
```

### Q18: LucentMist 本身占多少内存？

| 组件 | 内存占用 | 说明 |
|------|----------|------|
| CLI (scan 命令) | ~50 MB | 纯扫描，无 LLM |
| CLI (agent 命令) | ~80 MB | + OllamaProvider |
| API 服务 | ~80 MB | ASP.NET Core |
| Ollama (llama3.1:8b) | ~5 GB | GPU 或 CPU |
| 总内存（Agent 模式） | ~5.1 GB | LucentMist 本身很轻 |

### Q19: 并发数设多少合适？

实际测试参考值：

| 网络环境 | 推荐并发 | 备注 |
|----------|----------|------|
| 本机 (127.0.0.1) | 不限 | 不经过网络栈 |
| 有线局域网 | 200-500 | 延迟低 |
| 家庭 WiFi | 50-100 | 干扰多 |
| 远程 VPN | 20-50 | 高延迟 |

过高可能触发路由器限速或当成攻击行为。

## 平台差异

### Q20: Windows 上需要管理员权限吗？

**A**：
- **ICMP Ping**: Windows 上 `Ping.SendPingAsync()` 通常不需要管理员权限
- **TCP 端口扫描**: 不需要管理员权限
- **如果遇到 "Access denied"**: 以管理员身份运行终端

---

### Q21: macOS 上扫描无结果？

macOS 对原始 Socket 有更严格的安全限制。TCP Connect 模式不需要特殊权限，应该可以正常工作。如果遇到问题：

```bash
# 测试本机
dotnet run --project src/LucentMist.CLI -- scan 127.0.0.1

# 如果本机能通但局域网不通 → 检查 macOS 防火墙
# 系统设置 → 网络 → 防火墙 → 关闭或允许入站连接
```

---

### Q22: Linux 上需要 sudo 吗？

**A**：当前版本使用 TCP Connect 模式，不需要 root 权限。

```bash
# 可以直接运行（不需要 sudo）
dotnet run --project src/LucentMist.CLI -- scan 192.168.1.0/24
```

---

### Q23: 为什么虚拟机网络扫不到设备？

VMware/Hyper-V/VirtualBox 创建的虚拟网络适配器（如 192.168.12.0/24）：
- 默认是 NAT 模式：虚拟机可以访问外网，但宿主机扫不到虚拟机
- 需要改为**桥接模式**：虚拟机和宿主机在同一子网，才能互相扫描

```bash
# 方式1: 修改配置
# config/appsettings.json → Logging.Level = "Debug"

# 方式2: 环境变量
# Windows PowerShell
$env:DOTNET_ENVIRONMENT = "Development"
# Linux/macOS
export DOTNET_ENVIRONMENT=Development

# 方式3: 运行时指定
dotnet run --project src/LucentMist.CLI -- scan 192.168.1.0/24 \
  --logger console:minimumlevel=Debug
```
