名称和 MAC 仍不是身份认证；同一物理设备的最终确认来自用户指定的合并动作。

## 根因与修改

实现提交：`df52906b`。真实 CLI 集成回归和本记录另作独立提交。

1. 原 `RenderDevices` 无条件逐 MAC 渲染，已有关联只是技术字段，旧新身份仍被画成两台。
   现在按确认/疑似关联组织行，旧身份作为取代说明，其他离线记录单独分区。
2. 原匹配器对已存在且没有 Association 的 MAC 直接返回。用户的新 MAC 已被旧版存过，
   后续扫描永远无法补关联。现在重新评估这些旧格式记录，确认过的关联仍保留。
3. 新增 `monitor --merge <旧IP/MAC> <新IP/MAC>`。该命令本身是显式确认：
   只在同网段、明确已观测 MAC、新端有有效观测且旧端不同时在线时执行。
   IP 对应多个历史 MAC 则拒绝猜测，要求指定完整 MAC。
4. 合并在同一 SQLite 事务中迁移最早 FirstSeen、逐端口较新证据和已有信任，
   保存 `identity_merged` 记录，并将旧 MAC 归档到当前身份。
   保留原表、主键和 JSON 格式；仅增加可选 `MergedIntoId`，不删除旧原始记录。
5. 疑似关联告警升为 medium，写清旧 IP/名称、新 IP和可直接执行的确认命令。
6. 实测中继续修正两个呈现/状态问题：确认归档不再使后续每轮永久 partial；
   两端原本未信任时显示“原身份也未信任”，不再显示容易误解为拒绝迁移的“不继承信任”。

未修改 Agent、漏洞报告、发现协议或 ScanStore；未引入依赖。普通扫描不自动确认、不自动迁移新随机 MAC 信任。

在项目根目录打开 PowerShell。IP/MAC 仅对应本次用户已经确认的案例；其他设备必须先核对归属。

dotnet $cli monitor --devices --subnet 192.168.99.0/24
dotnet $cli monitor --once --subnet 192.168.99.0/24 --ports 22,53,80,443

本轮已生成两个真实在线备份：

- `data/monitor-before-confirm-20260907.db`：改动真实基线前的恢复点。
- `data/monitor-merge-real-rehearsal-20260907.db`：关联后备份；仅在此副本上执行旧 MAC `--trust`，用于正向迁移验收。

日常库没有被本次测试擅自增加 Android 信任。若用户以后决定信任，可对当前 MAC 执行 `--trust`。
合并不能修改手机/路由器配置；旧 IP 不能 ping 通属于历史身份，不会因合并重新分配 IP。

## 边界

- 两端同时响应时可能真是两台设备；不为满足“一条”而隐藏冲突。必须复扫确认，不强行合并。
- 未来出现另一个新 MAC 仍需再次核对；这不是网络准入或密码级身份认证。
- 源记录/告警没有被删除；旧版本不认识归档视图，不要同时运行新旧版本。
- 没有单次合并撤销命令；误并后可使用合并前备份按既有恢复手册恢复。
- 本轮不推送、不发布镜像；没有使用 LLM key。
