# monitor 随机 MAC 身份关联验证（2026-09-07）

## 范围与结论

本次只修改 monitor 的设备关联、信任呈现和对应测试，未改 Agent、报告、扫描协议或 ScanStore。
沿用现有发现链路提供的名称/mDNS 数据，未新增网络探测、NuGet 依赖、设备认证或自动信任功能。

**通过：独立进程 CLI + 真实 SQLite 的命令序列回归。未执行：物理 Android 设备更换随机 MAC 后的现场验证。**
网络发现输入为受控快照，不把测试夹具当成真实手机，也不声称证明设备一定广播名称。

## 旧问题的实际复现（RED）

基线提交：`ba0da8d2`。先添加命令序列回归，再运行原有生产代码：

1. `monitor --once --subnet 192.168.77.0/24 --ports 80` 建基线。
2. `monitor --trust 192.168.77.2` 信任旧 MAC。
3. 快照中的 `android-99.local` 换为新 IP/MAC，名称仅大小写和末尾点变化。
4. 再运行 `monitor --once ...`。

`RandomMacRotation_AssociatesHostname_WithoutStrangerAlertOrTrustInheritance` 真实失败：
`Assert.DoesNotContain("new_device", update)`，实际 CLI 输出包含：

```text
high 192.168.77.3
new_device：发现新的未信任设备（可能陌生设备）...
```

原因：原基线仅以 MAC/IP 键比对；已经采集的主机名/mDNS 名称没有参与身份关联。

## 修复语义

- 随机/本地管理 MAC 使用同网段名称证据匹配。大小写、末尾点和 `.local` 后缀规范化。
- 唯一历史名称、没有同时响应或型号冲突：`possible_same_device`，展示“疑似同一设备”。
- 多个历史匹配、同时在线同名、型号冲突：`identity_conflict`，展示“身份待核实”，不合并。
- 无有效名称：`identity_unconfirmed`，说明未取得证据，不直接认定陌生设备。
- 相同服务类型、端口、厂商不是唯一身份依据；未知文本不匹配，不猜型号。
- 旧 MAC 行、时间、信任、端口基线保留。新 MAC 单独存储，**不继承信任或端口历史**。
- 关联状态/关联对象没有变化时不重复产生关联告警；疑似别名的旧行不同时报“消失”。
- 连续更换 MAC 追踪到同一个疑似历史根；循环/损坏关联不循环运行，也不强行合并。
- 名称和 MAC 未经认证；即使唯一匹配也不是身份确认。已发生冲突不会因后续只看到一台而自动消除。
- 原表结构、主键、信任表不变；仅在既有 JSON 增加可选 `Association`。
  测试用 SQLite 删除该字段形成旧格式记录，重新打开、关联，确认旧信任和时间保留。
