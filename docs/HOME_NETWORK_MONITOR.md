# 家庭网络监控与基础诊断（当前源码）

本功能是**监控 + 告警 + 建议**，不是自动修复、设备准入或隔离系统。
没有 ZTE 网关管理权限，就不能替你修改路由规则、断开陌生设备或安装固件。
发现异常后由你核对并手动处理；不能登录路由器时联系网络管理员/运营商。
这次改动尚未发布为新 GHCR 镜像，使用包含本功能的源码构建，不要假定旧 0.9.8 镜像有 `monitor`。

## 1. 开始监控

在项目目录打开 PowerShell；不需要 API、Web、Ollama 或 DeepSeek key。

```powershell
dotnet build -c Release
$env:LMIST_DB = Join-Path (Get-Location) 'data/lucentmist.db'

# 先跑一次，核对是不是你有权监控的家庭网段。
dotnet run --project src/LucentMist.CLI -c Release --no-build -- monitor --once --subnet 192.168.99.0/24

# 确认首轮设备后持续运行；每轮结束 30 分钟后开始下一轮。
dotnet run --project src/LucentMist.CLI -c Release --no-build -- monitor --interval 30 --subnet 192.168.99.0/24
```

`watch` 是 `monitor` 的别名。如果已安装 `lmist` CLI，可将前面的 `dotnet run … --` 换成 `lmist`。
省略 `--subnet` 时，使用 `get_my_ip` 的同一主接口选择器推导 `/24`，不把 VMnet/WSL 网卡当物理主接口。
它不是路由查询；多网卡、VPN、非 `/24` 家庭网络请明确指定范围。

| 参数 | 行为 |
| --- | --- |
| `--interval 30` | 分钟，默认 30，允许 1～1440；不是“每个整点”，扫描期间不再排下一轮 |
| `--subnet 192.168.99.0/24` | 私有 IPv4 或回环地址，`/24`～`/32`，最大 256 地址；禁止监控公网 |
| `--ports 22,53,80,443` | TCP 端口列表/范围，最多 64 个；默认 `22,53,80,135,139,443,445,3389,8080,8443` |
| `--once` | 只跑一次；恢复已有基线并对比，不会每次重置 |
| `--cycles 2` | 跑指定轮数后退出，便于短时间验收；不能与 `--once` 同用 |
| `--devices` | 读取已存设备，不扫描；显示最后观测时间，不保证现在在线 |
| `--alerts --limit 100` | 查最近告警，默认 100，最多 1000；不扫描 |
| `--trust <IP或MAC>` | 标记你已核实的设备，下节解释身份边界；不扫描 |
| `--check-vulns` | 额外执行现有漏洞检查；默认不开启，避免每轮都查云库 |

首次**成功且非空**的发现建立基线，不把每台现有设备都报成“新接入”。
但“已在基线”不等于“可信”：请自行核对最初列表中有没有陌生设备。
后续发现新的未信任标识，才产生新设备告警；随机/本地管理 MAC 先走下述身份关联与核实，
不直接标成“陌生设备”。每轮显示完整设备列表。

**范围只由规范化网段决定。** `--devices/--alerts/--trust` 不需要重复扫描时的 `--ports`。
`--ports` 只控制本轮扫描范围，不再建立另一张设备表。换端口集合时保留各端口的历史观测时间，
只比较实际扫描且曾有基线的端口，不把“这次没扫描 443”误报为“443 关闭”。首次检查的新端口先建立该端口的基线。
首轮无告警是预期行为，不为了让 `--alerts` 非空而伪造“新接入”。

升级前停止旧 monitor 并使用 `backup` 备份数据库。首次打开旧库时，程序会在一个事务内合并
`网段|端口` 旧范围，保留设备、最初/最近出现时间、信任标记、告警 ID 和逐端口证据；损坏数据导致迁移失败时回滚。
不要同时运行新旧版本监控；旧版不认识新范围，若需降级请还原升级前备份。

## 2. 信任自己的设备与查看变化

先核实设备归属。下面的 IP 只是示例，应替换为刚才实际发现的设备：

```powershell
dotnet run --project src/LucentMist.CLI -c Release --no-build -- monitor --subnet 192.168.99.0/24 --devices
dotnet run --project src/LucentMist.CLI -c Release --no-build -- monitor --subnet 192.168.99.0/24 --trust 192.168.99.5
dotnet run --project src/LucentMist.CLI -c Release --no-build -- monitor --subnet 192.168.99.0/24 --alerts
dotnet run --project src/LucentMist.CLI -c Release --no-build -- audit --limit 10
```

传 IP 时，必须已有唯一、最近有效观测的 MAC；实际信任的是那个 MAC，**不是永久信任可被 DHCP 复用的 IP**。
也可直接填设备的有效 MAC，提前登记。无 MAC 时可以按 IP 对比，但拒绝永久信任该 IP。
MAC 能伪造，手机隐私 MAC 会随机化；此白名单只降低“陌生设备”提示，不是认证或网络准入。
已信任设备仍会有端口、服务和漏洞候选变化告警。

| 告警 | 级别 | 怎么理解、怎么做 |
| --- | --- | --- |
| 新的未信任设备 | 高 | 不涉及随机 MAC 疑似关联的新增标识；对照家庭设备后再信任，不是入侵确认 |
| 疑似同一设备 / 随机 MAC 未取得关联证据 | 低 | 名称唯一匹配则展示关联，否则身份待核实；不自动信任新 MAC |
| 同名设备/型号证据冲突 | 中 | 身份待核实，不按枚举顺序挑一个，不合并设备或继承信任 |
| 新增 TCP 端口 | 中 | 核对是否新开服务；在对应设备关闭不需要的服务/调整本机防火墙，不直接当作入侵 |
| 服务/厂商证据变化 | 中 | 对照软件升级、设备更换与真实指纹，不能用一次弱指纹认定被攻击 |
| 新漏洞候选 | 高 | 仅 `--check-vulns`；对照固件/软件版本和厂商公告，候选不是确认漏洞 |
| 已知设备未见/重新出现、IP 变化 | 低 | 睡眠、离线、DHCP 或探测被过滤都可能造成变化 |
| 端口本次未连接成功 | 低 | 可能关闭、过滤、暂时不可达；不声称确定“关闭” |
| 发现/端口未完成 | 低 | 保留有效基线，检查扫描权限与网络；无告警不等于安全 |

`--check-vulns` 的来源超时、服务识别失败等显示为单独的“检查状态”，保存在设备最近记录中，
不再产生 `analysis_incomplete` 告警。旧库中的该类历史行仍保留，但不在告警列表中挤占新设备变化。
`--devices`、`--alerts` 与每轮扫描均能看到这些状态；默认展示前三条并说明剩余数量。

无变化不重复生成告警。首次发现的漏洞候选会记录，历史候选不会因一次失败/云源超时被自动标成“已修复”；
当前实现也不自动清除已解决漏洞的历史记录，请重新运行 `vuln-scan` 并人工核实。
基线中的服务是观测到的产品/版本指纹，不用易变的 HTTP 日期等原始文本作比较。

## 3. 漏洞检查的开关与边界

```powershell
# 只使用内置离线规则；仍会对所选局域网目标发协议探测。
$env:LMIST_CVE_EXTERNAL = 'false'
dotnet run --project src/LucentMist.CLI -c Release --no-build -- monitor --interval 60 --subnet 192.168.99.0/24 --check-vulns
```

默认监控只发现设备、端口和服务，不声称做过漏洞检查。显式加 `--check-vulns` 时：

- 复用本轮成功端口扫描的 `open_ports`，失败不冒充“无开放服务”。
- 使用现有 `vuln_scan`，不默认调用 Nmap；不执行利用、登录、配置下发。
- 云源开关沿用 `LMIST_CVE_EXTERNAL`。未显式关闭时，现有漏洞工具会查询免费云源；需要控制外发则明确设为 `false`。
- 只把 `findings` 形成漏洞候选告警，不把大量泛关键词 `cloudCandidates` 当目标漏洞。
- 目标不公开固件/软件版本时仍可能无法匹配。来源不完整显示检查状态，不用“没新 CVE”证明设备安全。

## 4. 出问题时运行诊断

```powershell
dotnet run --project src/LucentMist.CLI -c Release --no-build -- diagnose
dotnet run --project src/LucentMist.CLI -c Release --no-build -- diagnose --gateway 192.168.99.1 --dns-name example.com
# 仅禁用公网 TCP 检查；DNS 查询仍会运行，不是完全离线模式。
dotnet run --project src/LucentMist.CLI -c Release --no-build -- diagnose --no-external
# 查看默认折叠的回环/高位监听端口（仍不代表公网可达）
dotnet run --project src/LucentMist.CLI -c Release --no-build -- diagnose --all-listeners
```

检查共享物理主接口、网关存活（复用 ICMP/TCP 回退）、本机解析器查询 `example.com`、
固定公网 TCP `1.1.1.1:443`、`8.8.8.8:53`、`223.5.5.5:53` 和本机 TCP 监听。
三个端点并发检查，每个最多 6 秒，逐个标成功/失败；不是服务漏洞扫描，不发送应用请求或扫描报告。
任一成功就有公网可达证据；全部失败也只说明这些端点不可达，不证明整个互联网中断。
默认会有 DNS/固定外网连通请求，**不是“零外呼”**。
DNS 可能命中本机缓存，不能据此证明网关 DNS 或某个特定解析服务器正常。

典型建议：

- 网关正常、公网 TCP 正常、DNS 失败：先检查本机 DNS/缓存，换域名复查，再联系路由管理者。
- 网关探测失败、公网 TCP 正常：网关可能只是不答探测，不能断言网关掉线。
- `1.1.1.1:443` 失败但其它端点可达：显示部分端点失败，已有公网可达证据，不判整体断网。
- 本机监听默认优先列非回环、非高位端口，折叠回环和 49152+ 端口并显示数量；高位端口不等于安全。
  `--all-listeners` 可展开（最多 64 条，超出会提示）；监听不等于从互联网可访问。

### 安卓、隐私 MAC 与设备型号

私有目标的 mDNS 定向探测现在包括 `_android._tcp`、`_adb._tcp`、`_adb-tls-connect._tcp`、
`_adb-tls-pairing._tcp`，以及既有的 Google Cast/device-info。跟随关联的 PTR/TXT/SRV，
每目标最多 20 次查询、总预算 1.2 秒。UPnP 继续复用 UDP 1900 的只读 SSDP/设备描述探测。
不因随机 MAC 而跳过探测；有名称/型号声明就显示证据，没有就保留未知。

ADB 默认是 **TCP 5555**，不是 UDP 5555；这轮不发送无效 UDP 5555 数据、不执行 ADB 连接、配对或命令。
服务声明是未经认证的设备线索，不能仅凭 `_adb` 或 `android-99.local` 猜手机品牌型号。
无线调试关闭、组播/定向应答受限或设备休眠时可能无回应；“未收到有效响应”不等于证明“设备从未广播”。
依据：[Android ADB Wi-Fi 文档](https://android.googlesource.com/platform/packages/modules/adb/+/HEAD/docs/dev/adb_wifi.md)。

监控现在复用已取得的主机名/mDNS 名称，在同一网段内对随机/本地管理 MAC 做疑似关联：

- 名称忽略大小写、末尾点和 `.local` 后缀；唯一历史设备匹配且没有同时响应/型号冲突时，标“疑似同一设备”。
- 仅有相同服务类型（例如两台都广播 `_adb`）、厂商、端口或 IP，不足以关联；未知占位文本不参与匹配。
- 同名设备同时出现、多条不属于同一疑似关联链的历史记录、或型号冲突时，标“身份待核实”，不自动解除已有冲突。
- 未取得有效名称时说明缺少证据，不直接报“陌生设备”；本地管理位不是 Android 或随机化的确定证明。
- 旧 MAC 的设备行、最初/最近出现时间、信任和端口历史保留。新 MAC 单独保存，**不继承信任或端口基线**。
  不把疑似换 MAC 同时报成“旧设备消失 + 新陌生设备”。重复同一关联状态不刷告警。
- 核对手机 Wi-Fi 私有地址后，对新 MAC/IP 再执行 `monitor --trust`；界面明确显示这是对当前 MAC 的显式信任。
  名称和 MAC 都可伪造，疑似关联不是身份认证。

此修改只在原 `state_json` 增加可选关联信息，不改变表、主键或信任表；旧数据缺少该字段仍可读。
独立进程 CLI 回归覆盖了换 MAC、信任和冲突流程；真实手机手动切换随机 MAC 尚未实测，
见 [随机 MAC 关联验证](monitor-random-mac-validation-2026-09-07.md)。

诊断退出码：`0` 已执行检查无失败/警告；`2` 有检查失败/警告；`1` 参数或运行错误。
`--no-external` 跳过项不是通过项；读完整表格，不只看退出码。
有限轮数监控发现无法应用基线时返回 `2`；Ctrl+C 正常停止返回 `0`，不等于网络安全。

## 5. 长期运行、数据与恢复

`monitor` 是持续运行的 CLI，不是安装到系统的守护服务。终端/进程退出、电脑休眠时不监控，
关闭终端不会“仍在后台保护”。Ctrl+C 停止；重启同一命令/数据库恢复已有基线。
需要无人值守时可由 Windows 任务计划程序以你的账户启动 `dotnet`：
参数为已构建 `lmist.dll` 的绝对路径加 `monitor ...`，设置项目为工作目录、相同 `LMIST_DB`，
并设置“已有实例则不启动新实例”。本工具不替你安装启动项、不存路由器凭据。
Linux 可由用户自己的进程管理器运行同一 CLI；本轮真实网络验收在 Windows，未声称 Linux 实机已测。

- 每轮三分钟总预算，设备端口扫描最多 2 台并行、每台 16 个 TCP 连接；发现阶段沿用有界并行 32。
  这些数字不是包含所有元数据探测的全局套接字上限。每轮结束后才等待间隔，不追赶积压轮次。
- 同一数据库/范围只允许一个监控进程（文件租约，进程退出自动释放）；读告警/信任标记不需要停监控。
- SQLite 默认 `data/lucentmist.db`，可用绝对 `LMIST_DB`；**明文**保存 IP、MAC、名称、厂商、端口和告警。
  表为 `monitor_state`、`monitor_devices`、`monitor_trust`、`monitor_alerts`，每轮基线与告警在同一事务提交。
- 发现失败、全网段零响应或重复设备标识时不覆盖基线，不产生“所有设备消失”。
  端口扫描失败保留上次端口和观测时间。数据库不可写会明确退出，不假装告警已保存。
- 已知 IP 本轮有响应但丢失 MAC 证据时，显示“身份未确认”，不同时报新设备与原设备消失。
  该记录的历史信任不适用于当前响应，端口也保留历史时间；其他新设备仍正常告警。
  重新观测到原 MAC 后恢复正常比对；相同 IP 出现不同 MAC 仍需重新核对，不能按 IP 继承信任。
- `audit` 可看每轮摘要（发起者 `cli-monitor`）。监控告警目前无自动删除策略，请定期备份并关注磁盘空间。
- 沿用现有 [备份/恢复手册](SELF_USE_GUIDE.md)：`backup` 的 SQLite 在线备份会包含这些新增表；
  不直接拷贝仍运行中的 `.db` 忽略 WAL。恢复前停止 API/Web/monitor，先备份当前数据，再按手册恢复。
- 无邮件、手机推送、Web 监控页、自动漏洞修复或隔离。客户端看不到路由器全部接入记录；
  休眠/不回应探测的设备可能漏发现，不能称为实时“陌生设备零漏报”保障。

真实结果和未完成的物理设备接入测试见 [监控验收记录](home-monitor-validation.md)。
